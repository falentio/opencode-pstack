### Prototype

**You own the design decision, not the code.** Treat the prototype as a throwaway instrument. The real build follows Feature. Use this playbook for "prototype", "mock it up", "sketch this", "try this layout", or for exploring a UI, interaction, or layout before committing. Also use it to settle an empirical fork, such as behavior, timing, or approach, by observing it run when a quick sketch can answer the question instead of asking the human.

This is the one playbook where the Laziness Protocol's "smallest change" rule and the verification bar invert. Prioritize speed over polish. Code quality does not matter here. Do not plan the prototype. The rigor is in picking the right design cheaply. Be bold. Propose variations the user did not ask for. Throw an approach away and try another.

1. Scope the decision the prototype exists to make. Name the layout, interaction, density, behavior, timing, or approach under consideration. No decision means no prototype. Route the request to Feature.
   **Completion criterion.** The decision is stated in one sentence. If no decision exists, the prototype has stopped and the request is routed to Feature.
2. Gather references when the design space is open. Search for prior art. Summarize a moodboard of themes, palettes, and layouts. Let the user pick directions before building. Skip this step when the direction is set.
   **Completion criterion.** The direction is set before step 3. When the direction was open, the prior art, moodboard, and user-picked direction are recorded. When the direction was already set, this step is marked skipped.
3. Build the throwaway in an isolated scratch directory that is separate from production source. For a visual decision, use vanilla HTML/CSS/JS or the lightest stack that renders the idea. Use CDN deps and a dev server with hot reload. For a behavioral or timing decision, use the smallest script that exercises the question. Use no production framework, tests, or abstractions.
   **Completion criterion.** The throwaway runs from the isolated scratch directory and remains outside production source. The visual branch uses the permitted lightest stack with CDN deps and hot reload, or the behavioral branch uses the smallest question-exercising script. No production framework, tests, or abstractions are present.
4. When comparing alternatives, build them behind one switcher. Use buttons or a keypress. Label each variant so the user can name it. This is the **exhaust-the-design-space** principle skill made cheap.
   **Completion criterion.** If alternatives are compared, one switcher exposes every labeled variant and the user can name each variant. If alternatives are not compared, record that this step is not applicable.
5. Verify on the matching surface. For a visual decision, screenshot each variant via the control skill and drive the interaction. The eye is the test. For a behavioral or timing decision, observe the thing you are deciding by logging the timing, printing the output, or watching the render. The observation is the test here, not an assertion.
   **Completion criterion.** For the visual branch, every variant has a screenshot and its interaction was driven on the matching surface. For the behavioral or timing branch, logs, output, or render observation show the behavior under consideration. The evidence is observation, not an assertion.
6. Present alternatives, tradeoffs, and a recommendation. The output is the decision plus the throwaway artifact, not shippable code. Hand the chosen direction to Feature, or to architect for the shape, for the real build.
   **Completion criterion.** The presentation includes the alternatives, tradeoffs, recommendation, decision, and throwaway artifact. The artifact is marked as not shippable. The chosen direction is handed to Feature, or to architect for the shape, for the real build.

**Reply:** List the variants explored, the evidence, the tradeoffs, the recommendation, and the scratch path. For a visual decision, include screenshots. For a behavioral or timing decision, include the observed output or timing. State plainly that the prototype is throwaway.
